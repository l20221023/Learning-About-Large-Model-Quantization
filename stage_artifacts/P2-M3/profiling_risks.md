# P2-M3 Profiling risks and measured handling

- **Built-in support boundary:** vLLM 0.26.0 contains Routed Experts Capture for the V1 runner. The V2 runner explicitly lists routed capture as unsupported. M3 therefore used V1 for both ON and OFF. This is documented as a runner change relative to the earlier Q1 server; the MoE backend remained TritonExperts.
- **Kernel effect:** `BaseRouter._select_experts` calls the capture callback on logical IDs before returning the same weights and IDs to the modular MoE runner. The capture does not replace Top-K or expert execution. Both ON/OFF selected the same TritonExperts backend.
- **CUDA Graph:** both paired runs used eager mode, so CUDA Graph replay was disabled. No graph capture/replay interaction was measured. Recheck if future runs change eager mode.
- **Synchronization and cost:** the built-in path writes IDs into a bounded device buffer and copies results into pinned host memory nonblocking at runner bookkeeping. The scheduler maps returned IDs through KV slots; the API serializes arrays to NumPy/base64. Do not assume zero overhead: ON added 0.606 ms mean TTFT, 0.810 ms mean request TPOT, and 19.661 ms mean client request time in this six-request sample.
- **Padding and repeated execution:** the capturer clears its per-step buffer; scheduler outputs are sliced by actual scheduled/prompt/output token counts and slot mapping. The independent audit checked exact row counts, no invalid IDs, six unique IDs per routed row, and cache-reused prompt rows. Preemption/speculative decoding and concurrent multi-request row mapping were not tested.
- **Request association:** one synchronous request was in flight at a time. Public response ID reliably associates returned route arrays with the client request; internal scheduler request ID is unknown. Do not infer internal IDs from output order.
- **TP accounting:** the returned array has one logical route row per processed token and MoE layer, not one row per TP rank. M3 counts one set of six IDs, never two. TP1-vs-TP2 route IDs differed for 688/4550 aligned prompt token/layer rows; reason remains unknown without TP2 rank-level router logits.
- **Memory metric:** GPU memory sampled at 250 ms. CPU memory uses summed process-group RSS, which can double-count shared pages. No PSS/cgroup memory series was captured.
- **External validity:** N=6 per mode, one run each, 24 output tokens per request. Reported overhead is a controlled pilot, not a full performance baseline or a statistical estimate.
